# Authority and Canon

## Purpose

Determine what the project establishes, which sources govern a question, and how conflicting statements should be handled. Do not impose a hierarchy merely because one is common in other projects.

## 1. Discover the project's authority system

Inspect, where present:

- repository-level instructions and contribution rules;
- project README and setting indexes;
- explicit statements such as "唯一总定义处", "以本文件为准", "冲突时按以下顺序裁决";
- document roles: overview, master setting, domain volume, appendix, timeline, reference, draft, notes;
- explicit versioning, supersession, and status conventions.

Record the actual rule and the file that states it. A filename such as `canon.md`, a newer timestamp, a longer document, or a more detailed explanation does not automatically make a source authoritative.

If the project does not define a conflict rule, do not invent one. Report the conflict and ask the author to decide, unless the task only requires a clearly labelled provisional interpretation.

## 2. Resolve evidence carefully

Use the following evidence categories unless the project defines its own compatible categories:

| Status | Meaning | Permitted use |
|---|---|---|
| Confirmed | Explicitly established by the author or by a source that governs the subject under project rules | May be treated as canon within its stated scope |
| Unresolved | Explicitly undecided, incomplete, or not consistently established | Must remain open |
| Inferred | A reasoned conclusion from available evidence, not directly established | May guide questions or proposals, never silently become canon |
| Deprecated | Explicitly withdrawn, replaced, or marked obsolete | Do not use as current canon; retain only when explaining history or migration |

Do not assign status from tone alone. A confident sentence in a draft is not automatically confirmed if the project identifies that draft as exploratory.

## 3. Distinguish scope from authority

A document may be authoritative for one subject but not another. For each relevant source, identify:

- subject it governs;
- scope and exclusions;
- whether it defines terms, summarizes them, or merely references them;
- whether it is current, historical, draft, or deprecated;
- any explicit links to governing documents.

A summary is not automatically a replacement for the source it summarizes. An appendix may be authoritative for its declared technical detail without overriding the main definition outside that scope.

## 4. Handle conflicting evidence

When two sources disagree:

1. Quote or summarize both statements accurately.
2. Give exact file paths and headings or line locations when available.
3. Check whether one source explicitly governs the subject or supersedes the other.
4. Check whether the apparent conflict is actually a difference in scope, time, perspective, or terminology.
5. If the project's rule resolves it, apply that rule and explain why.
6. If no rule resolves it, classify it as unresolved. Do not select the more convenient version.

Do not use recency, repetition, specificity, or narrative plausibility as a substitute for an explicit authority rule.

## 5. Preserve change history

When a definition or fact changes, retain enough history to explain the transition if the project tracks it. Clearly distinguish:

- current definition;
- former definition;
- reason or authorization for the change, if documented;
- files that still contain the former wording;
- whether old wording is a historical quotation or an accidental stale reference.

Never revive a deprecated concept because it appears in an old passage.

## 6. Evidence record

For any consequential claim, keep a compact evidence record:

- Claim:
- Status:
- Source file and section:
- Governing authority rule:
- Scope:
- Related or conflicting sources:
- Remaining uncertainty:

If source locations cannot be retrieved, say so rather than fabricating a citation or line number.
